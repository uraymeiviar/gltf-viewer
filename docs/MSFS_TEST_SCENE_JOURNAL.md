# MSFS Test Scene Journal

[ASOBO journal](ASOBO_EXTENSIONS_JOURNAL.md) · [Surface-data study](ASOBO_GBUFFER_STUDY.md) · [Exporter semantics](ASOBO_EXTENSIONS_SEMANTICS.md) · [Reference views](ASOBO_REFERENCE_VIEWS.md)

**Status:** Planned (2026-10-25). **Owner:** the user, supervising Gemini. Claude reviews the results that Glider
uses (manifest, captures, coverage).

## 1. Goal

Produce glTF test models that **MSFS 2024 renders**, plus screenshots of how it renders them, as ground truth for
Glider's ASOBO work (phases A1–A7). The models contain every MSFS material type and every ASOBO extension, for
both the interior and the exterior, laid out so one screenshot shows many controlled cases side by side.

This is a separate project. It produces **test data** for Glider; it changes nothing in the Glider repository
except, at the end, a manifest that points Glider's harnesses at the data.

**Deliverables:**
1. A Blender scene built by a script, so it can be regenerated (`build_scene.py`, run with `blender --background`).
2. Exported source glTF files (interior and exterior) and their textures.
3. A dedicated MSFS 2024 project (one test aircraft) that loads them, and its **packaged** output (the packaged
   glTF files declare `ASOBO_asset_optimized`, which Glider also needs to test).
4. MSFS screenshots from fixed cameras, including the developer-mode debug views (§6).
5. `manifest.json` describing every file, fixture, camera and capture (§7).

## 2. Constraints

- **Tools:** Blender 5.2 with the user's exporter `H:\git-repos\msfs-blender-5-addons\io_scene_gltf2_msfs_fss`
  (Asobo 8.4.1 + FSS fixes); MSFS 2024 SDK (docs at `F:\new-fss-aircraft-ejet\doc\msfs-sdk\pages`); the MSFS 2024
  package tool.
- **Location:** a new folder or repository, for example `H:\git-repos\msfs-test-scene` for the scripts and the
  project, and a data folder for the large outputs (exports, packages, screenshots). Never edit the E-Jet projects
  (`F:\new-fss-aircraft-ejet\...`, `G:\e-jets-e2\...`); copy what is needed.
- **Reproducible:** everything in the scene comes from `build_scene.py` and a parameter table (`fixtures.json`).
  No hand edits in the `.blend` file that the script cannot recreate.
- **Exporter only:** every material and extension is set through the exporter's MSFS material properties, so the
  glTF is exactly what a real project would contain. No hand-written glTF JSON in the MSFS files. (Glider-only
  synthetic fixtures are a separate thing and live in the Glider repo.)
- **Labels:** every fixture carries a readable label (a small unlit/emissive text plate, not a decal) with its id,
  so screenshots can be read without the manifest.

## 3. The MSFS project

One test aircraft, so interior and exterior cameras, the cockpit occluder, interior lights and windshield effects
all work as on a real aircraft.

- **Base:** copy a minimal aircraft from the SDK samples (or, as a fallback, the `fss-aircraft-e2-190` project
  structure) into a new project named for example `fss-test-scene`, with its own package name, title and ATC id, so
  it never conflicts with the real products.
- **Models:** `model/TestScene-Exterior-LOD00.gltf` and `model.interior/TestScene-Interior-LOD00.gltf` (names and
  folders as the base aircraft uses), one LOD each. A `model.xml` per model with no behaviours except what a test
  needs (for example, one emissive control).
- **Flight model:** whatever the sample provides; the aircraft only has to load, sit on the ground and be stable.
  Parking brake on, engines off unless a capture needs power.
- **Cameras:** fixed custom cameras in `cameras.cfg` for every capture view (§6), so screenshots are repeatable.
  The same views are also exported as **glTF cameras** in the scene, so Glider can attach to exactly the same view.
- **Gate T0** (below): the empty aircraft loads in MSFS 2024 from the project, and the package builds.

## 4. Scene layout

- **Exterior:** a simple fuselage-like body (a cylinder with a rounded nose, a flat side panel area and a wing stub)
  carrying test boards on its sides and on the ground next to it (a ground board in front of the aircraft). Boards are
  flat panels in a grid; each cell is one fixture.
- **Interior:** a box cabin around the pilot eye point with an opening (the windshield frame) at the front; test
  boards on the walls, the "panel" in front and the floor. The environment occluder covers this cabin.
- **Cell content:** a flat tile plus a sphere (or a rounded box) above it, so each fixture shows flat, curved and
  grazing-angle behaviour. Neutral grey surroundings, no other models.
- **Sweeps:** where a parameter matters, a row of cells sweeps it (for example 0, 0.25, 0.5, 0.75, 1).
- **Textures:** generated by the script (checkers, gradients, ramps, labelled normal-map bumps, ORM ramps), with a
  few real E-Jet textures copied in for realistic cases.

## 5. Coverage

Every exporter material type (22) and every ASOBO extension (Glider's support table) appears at least once. Rows
marked **Q** answer open questions from the [surface-data study §5](ASOBO_GBUFFER_STUDY.md); build those carefully,
they are the most valuable.

| Extension | Cases |
|---|---|

| `ASOBO_material_draw_order` | covered with decals and glass above |

| `ASOBO_material_pearlescent`, `ASOBO_material_iridescent` | colour shift / thickness sweeps on spheres |

| `ASOBO_material_alphamode_dither` | dither vs blend side by side |
| `ASOBO_material_antialiasing_options`, `ASOBO_material_disable_motion_blur` | a rotating part (property animation), flag on and off |
| `ASOBO_material_wind_flex`, `ASOBO_material_foliage_mask` | one card each |
| `ASOBO_material_dirt` (if the exporter writes it) | dirt amount sweep |
| `ASOBO_property_animation` | an animated emissive or UV offset |
| `ASOBO_normal_map_convention` | written by the exporter automatically; check it is declared |
| Lights: `ASOBO_macro_light` / street, advanced lights, sky portal | interior: one point and one spot light with interior flag on a white wall; exterior: a landing-light-like spot on the ground board; one sky portal in the cabin opening |

Anything the exporter cannot produce is listed in the manifest as not produced, with the reason.

## 6. Captures

- **Conditions** (record them all in the manifest): MSFS version and SU, graphics preset and the exact settings
  that matter (anti-aliasing mode, render scaling, SSR, sharpening off), time of day, weather preset, airport and
  parking spot, aircraft power state.
- **Standard set** per camera: noon clear sky; low sun (shadows, SSS, sail); night (emissive, lights); rain (windshield,
  occluder); snow (occluder).
- **Debug views:** MSFS developer mode can display individual channels (albedo, metallic, roughness, AO, world
  normal, depth, velocity, TAA mask, clear-coat roughness, interior mask; SDK `devmode/menus/options_info/
  channel-display.md`). Capture these for the decal, clear-coat and AO boards: they show the composited surface
  properties directly and are the best answer to **Q1–Q3** and **Q12**.
- **Cameras:** one per board (straight on), plus one grazing view per board with glass, clear coat or anisotropy.
  Name views `<area>_<board>_<variant>`, for example `int_decals_front`, `ext_glass_grazing`.
- **Format:** PNG, 1920×1080 at least, no UI (hide the toolbar), file name = view name + condition, for example
  `int_decals_front__noon.png`, `int_decals_front__noon__dbg_roughness.png`.

## 7. Manifest

`manifest.json` in the data folder, the only file Glider's harnesses read:
- files: source glTF paths, packaged glTF paths, texture folders;
- fixtures: id, material type, extensions, parameter values, board, cell, node name;
- cameras: name, glTF camera name, MSFS camera name, position and target;
- captures: file, camera, condition, debug view, MSFS version and settings;
- not produced: fixture id and reason.

## 8. Phases

Each phase ends with a check the user can do; Gemini works one phase at a time.

| Phase | Work | Gate |
|---|---|---|
| T0 | New folder/repo, MSFS project from the sample aircraft, empty test model, package build | Aircraft loads in MSFS 2024; package builds without errors |
| T1 | `build_scene.py` skeleton: body, cabin, boards, labels, cameras (Blender + glTF), `fixtures.json`, export + package script | Boards and labels visible in MSFS from every camera; glTF cameras match MSFS cameras |
| T2 | Standard material sweeps, alpha modes, emissive, AO, normal maps | Captures of T2 boards |
| T3 | Decal boards (all modes, Q1–Q3, Q5) | Captures incl. debug views |
| T4 | Glass and windshield boards, rain, icing masks, glass behind glass | Captures incl. rain |
| T5 | Layered BRDFs: clear coat, anisotropic, hair, SSS, pearlescent, iridescent, sail | Captures at noon and low sun |
| T6 | Detail map, UV options, parallax window, porthole, fresnel, ghost, dither, tire, propeller, trees, invisible, occluder, fake terrain | Captures |
| T7 | Lights, sky portal, shadow options, day/night, property animation | Night and low-sun captures |
| T8 | Manifest complete, packaged copies, coverage check against §5 | Every row in §5 is produced or listed as not produced |

## 9. Guidance for supervising Gemini

- Give one phase per brief, with the files it may create, and the gate as acceptance.
- Gemini reads the exporter code for property names (`blender/utils/msfs_material_utils.py` lists the material types
  and properties) and sets them from the script; it does not guess extension JSON.
- After every export, a quick check script lists each material's declared extensions and compares them with
  `fixtures.json`, so a wrong property name is caught before MSFS is started.
- Gemini cannot run MSFS or take screenshots; the user does T0–T8 captures. Gemini may prepare a capture checklist
  per phase from the manifest.
- Keep the E-Jet projects read-only, and keep generated data out of git (large binaries).
