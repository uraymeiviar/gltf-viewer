# MSFS surface-data dependencies — before A2

Evidence checked 2026-10-24. This is an inventory of semantics and data dependencies, not a G-buffer layout proposal.

## Evidence and scope

**[V] = verified by reading the cited source; [I] = inference from that source.** A verified exporter field or Blender preview is not verification of the MSFS runtime shader. “Reads” below distinguishes **local** inputs (textures, interpolants, material constants, lights) from **screen** inputs (previously rendered surfaces, depth, radiance, history). “Forward: yes” means no intrinsic requirement to modify another surface's attributes was found; this is an **[I]** feasibility judgment, not a statement about MSFS pass selection. Features on a decal receiver still supply their evaluated properties to whatever lighting/compositing path is used. [I; SDK-M:79,87,97; SDK-P:38–75]

## 4. Draw order and blending facts

1. **[V] Pass and receiver restrictions.** Default and frosted geometry decals are rendered between the SDK's named deferred and transparent passes. Multiple overlapping geometry decals should be in the same sub-mesh; first sub-material renders first. Default decal receivers are explicitly Standard, ClearCoat, Anisotropic, FakeTerrain and SSS. Glass is absent from this list, and windshield icing has its own material path. **[I]** Do not interpret frosted decal meshes as the windshield-icing implementation or extend the receiver whitelist without evidence. [SDK-M:87,97,101,131; SDK-A/windshield-and-windows:62–66]

2. **[V] Sort keys.** For decals, larger `drawOrderOffset` renders above smaller. For Glass/Windshield, it offsets the back-to-front distance measured at the **mesh bounding-box center**, not pivot. SDK UI range is −999…999. **[I]** This settles the earlier “additive distance or separate bucket?” question differently for decals versus glass; ties and precedence against sub-material order remain unspecified. [SDK-M:371; `docs/ASOBO_EXTENSIONS_SEMANTICS.md:220–222`]

3. **[V] Component rules, stated algebraically from SDK prose.** Let `b` be the existing background property, `d` the evaluated decal property, and `f` its named component factor: C, M, R, N and E use `lerp(b,d,f)`; O uses `lerp(O_b,O_d*O_b,f_O)`. Factor 0 preserves the background; factor 1 replaces the first group but **multiplies** occlusion. **[I]** The complete effective weight may also include decal opacity/masks; the SDK explicitly requires albedo alpha even for a normal-only decal, but does not specify the combined alpha×factor equation for every property. Normal interpolation coordinate frame/renormalization and linear-versus-encoded color interpolation are not supplied. [SDK-P:38–63; SDK-A/airframe-details:94]

4. **[I] Successive decals are order-dependent.** For an illustrative single property with two lerp factors of .5 and starting value 0: applying decal values 1 then 0 gives .25, reversing them gives .5. This follows from the documented lerp, not a measured MSFS screenshot. AO's pure product endpoints commute, but this does not make the full material stack commutative. [SDK-P:38–63; SDK-M:371]

5. **[V] `normalOverrideFactor` is separate from `normalBlendFactor`.** The normal-mode control chooses receiver mesh normal at 0, decal mesh normal at 1 and interpolates between them. `normalBlendFactor` controls the surface-normal component's blending contribution. **[I]** These represent different operations; replacing both with a single alpha loses the documented distinction. Exact tangent basis construction and order relative to normal-map sampling are unknown. [SDK-P:55–71; PROP:91,94; E/asobo_material_geometry_decal:34,37]

6. **[V] Coat placement.** `underClearcoat` defaults true in this exporter; Blender's checkbox means under, unlike 3DS Max's over checkbox. Coat RGB, R and N are independently defined. **[I]** Below-coat decals must influence the base appearance before the coat's lighting/absorption is resolved; a single post-lighting color overlay cannot generally preserve this. The sources do not identify separate overcoat factors, a coat-amount decal channel, or which layer receives an overcoat normal/roughness decal. [PROP:99,158–164; SDK-P:73–75; SDK-T:144–148]

7. **[V] Mask sharpness conflict.** SDK says smaller Blend Sharpness makes a sharper mask. The Blender preview computes bounds `clamp(mask.r − (1−s),0,1)` and `clamp(mask.r + (1−s),0,1)`, uses vertex A×(1−threshold) in a linear range map, then multiplies standard alpha; thus larger `s` narrows the preview ramp **[I]**. The preview adds an epsilon to sharpness. The threshold/freeze controls are not in the decal extension parameter list. **[I]** This is a documentation-versus-preview conflict, not a verified engine equation. [SDK-P:422–424; B/msfs_material_geo_decal_blendmasked:263–344,407–415; E/asobo_material_geometry_decal:30–45; PROP:95–98]

8. **[V] Exported defaults and missing keys.** Six factors and normal override default 1, sharpness 0, undercoat true; the writer elides defaults. `mode` is always written for new decals. Only default mode forces all target-channel booleans into output; frosted/blendMasked do **not** serialize those channel booleans through this writer. **[I]** Importer/UI defaults are not verified MSFS defaults for omitted keys. Both schemas list only enabled and six factors; they omit mode/mask/override/sharpness/undercoat/channel booleans. [PROP:88–102; E/asobo_material_geometry_decal:30–45,104–145; S/ASOBO_material_geometry_decal:6–30; S/ASOBO_material_blend_gbuffer:6–30]

9. **[V] Legacy equivalence boundary.** The importer synthesizes default mode for `blend_gbuffer`, and SDK release notes call that name deprecated decals. **[I]** Reusing the modern blend rules is a justified working interpretation, not proof that every legacy mode, default, depth rule or alpha path is identical. There is no verified special ordering rule between legacy and modern decals. [E/asobo_material_geometry_decal:57–64,89–94; SDK/introduction/sdk-release-notes.md:511]

10. **[V] Other alpha behavior.** BLEND is documented as Porter–Duff over. The SDK MASK overview says alpha **above** cutoff is discarded, but its later Alpha Cutoff section says alpha **greater than or equal** cutoff is opaque; the Blender preview earlier studied uses `>`. **[I]** Treat the contradictory overview as unresolved text, not a reason to invert mask coverage. Dither pattern, temporal phase and shadow coverage are unspecified. [SDK-M:349,353,357,469; B/msfs_material:1596–1669; `docs/ASOBO_EXTENSIONS_SEMANTICS.md:244–263`]

## 4a. Web sources: EnvironmentOccluder and FakeTerrain (added 2026-10-24)

The local SDK only gives one line for each, so the online MSFS 2024 SDK and the developer forum were searched.

- **[V] EnvironmentOccluder is a volume, not a surface property.** The MSFS 2024 SDK page on cockpit collision
  meshes and occluders says the occluder is one mesh covering the whole cockpit and cabin, with normals facing
  *outward*, on its own layer, exported only for LOD0. With it, environmental effects and objects (the page names
  rain, snow and trees) are no longer visible inside the cockpit. Test: maximum snow, or slew into foliage, and
  "see none of the environmental details passing through the fuselage". The mechanism is not described.
  [docs.flightsimulator.com, msfs2024 › models-and-textures › modeling › aircraft › cockpit ›
  cockpit-collision-meshes-and-occluders]
- **[V] Forum reports:** it also cuts through fog, so use it only on the top LOD; it does not stop snow
  *accumulation*; some occluders were visible in MSFS 2024 builds (workaround alpha 0); the old Blender preview drew
  it translucent green. [devsupport.flightsimulator.com threads 4068, 10775, 3143]
- **[I] Consequence for Glider:** the occluder writes no PBR property and receives no decals. It masks *environment*
  rendering (precipitation particles, vegetation, fog) inside its volume. Glider draws none of those, so the
  occluder only needs to be **not drawn as a surface** (as `ASOBO_material_invisible`), with an optional debug
  overlay. It needs no G-buffer channel. If Glider ever draws rain or fog, it would need an occluder volume mask
  (depth of front and back faces), which is separate from the material G-buffer.
- **[V] FakeTerrain** is "the terrain material type": meshes using it get the same shading system as the simulator's
  terrain; no extra parameters (MSFS 2024 FlightSim Materials page, 3ds Max plugin Materials page). It is one of the
  five decal receivers. Asobo states there is no terrain–object material blending feature in MSFS 2024
  (devsupport thread 18064), so FakeTerrain is not a blend into real terrain.
- **[I] Consequence for Glider:** without a terrain renderer, FakeTerrain is shaded as a standard opaque PBR receiver
  (terrain-specific lighting is unknown). It needs a receiver flag only if its lighting later differs.
